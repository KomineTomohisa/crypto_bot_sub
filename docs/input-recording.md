# 本番入力の記録とオフライン再生

## 同じ履歴を使う

`strategy_inputs.py` の `prepare_strategy_inputs` をliveとbacktestの両方から呼ぶ。履歴の開始は、観測時刻のJST日付0時から2日前。方式IDは `jst_prior2_calendar_days_v1`。EMA等の初期化位置、MACD正規化の母集団、シグナル計算の入力範囲を共通にする。API応答・キャッシュがこの範囲より長くても、特徴量を作る前に範囲外を除く。

15分足は、観測済みの未確定足を1本含められる。1時間足は確定済みだけを使う。過去の始値での判断には、その足の高値・安値・終値を始値、出来高を0にした観測を渡す。過去の足終了時の代理観測では、足終了直前を特徴量の観測時刻とし、その足の完成OHLCVを渡す。これは15分足による近似であり、本番の足内の監視系列までは復元しない。

backtestでは各観測ごとに共通処理を実行するため、全期間を一括で指標計算していた場合より計算時間が増える。異なる観測時点の指標を流用する最適化は行わない。

## 保存先と内容

`run_live` 開始時に記録を有効化する。保存先はbotの `log_dir/input_events/`。

- セッションファイル：UTC日時とランダムIDを含む `.jsonl`。日付変更時にはUTC日付単位で次のセッションへ切り替える。
- 入力データ：`blobs/<SHA256>.json.gz`。特徴量へ実際に渡した、時刻正規化済みのOHLCVを圧縮保存する。同一ハッシュの内容は同一データ。
- 開始時：ソース内容のハッシュ、Python・pandas・NumPyのバージョン、選択したシグナル設定、建玉等の開始状態。
- 特徴量：入力データへの参照、履歴方式、計算結果のハッシュ、欠損している確定足区間数。
- 価格・余力：botが実際に取得したGMOのbid/ask/lastと取引所時刻、必要余力、取引ルール・数量・費用率、参照した余力。
- 判断：エントリー方向と待機状態、決済の入力水準・価格・保有時間・Short利益保護の前後状態と判断結果。
- SR・注文結果：実際に参照したSR候補と設定、受付・約定結果の主要項目、決済損益・費用の主要項目。
- 取得失敗：価格取得の各試行と例外の種類、足取得不能や銘柄処理の失敗。

公開価格は現在のbotがRESTで観測した応答を記録する。市場の全ティックをWebSocketから新規収集する機能ではない。APIキー、シークレット、認証ヘッダー、パスワード、トークンは記録しない。設定・応答全体のダンプは行わず、明示した項目だけを保存する。

自動削除は行わない。ログと圧縮データの両方をセットで保管する。ファイルへの保存はバックグラウンドで行い、売買処理はディスク書き込みの完了を待たない。待機キューの上限は128件で、混雑してイベントを落とした場合はそのセッションを不完全にする。終了時は最大2秒間の書き出し完了を待ち、間に合わなければ完全とは認定しない。保存失敗時も決済監視・取引所の約定確認は続け、記録失敗を理由に注文を再送しない。

`order_result`は通常の発注経路と未確定注文の回復経路で共通化する。元の判断時の特徴量参照を保存し、回復時の別の特徴量へ付け替えない。同一プロセスでの同じ注文状態の再記録は抑止する。

DBでの確定直後・イベント保存前に強制終了しても、次の起動時に確定済み注文から1サイクル最大16件ずつ補完する。再起動による再配信には同じ`event_id`を付けるため、**複数セッションの注文結果を集計するときは`event_id`で重複を除く**。未確定から確定への状態変化には別IDを使い、約定数量等はその時点の累積値として扱う。補完は注文結果の記録であり、失われた市場入力・判断イベントまで復元するものではない。

## 破損・欠損を見分ける

各行にセッションID・連番・前の行のハッシュ・受信時刻・単調増加時計・内容ハッシュを保存する。途中行の削除、順序の入れ替え、重複、内容変更、書きかけの行、入力blobの欠損・破損を検出する。通常終了・日付切り替え時には終了行を書き、保存失敗があれば完全なセッションとしない。

これは偶発的な欠損・破損の検出であり、外部の署名や悪意ある全面書き換えに対する認証ではない。強制終了したセッションや、記録開始前・記録対象外の出来事を完全と判定しない。市場データ自体の欠損は、記録ファイルの整合性とは別に `missing_closed_intervals` で表示する。

## オフラインで検証する

同じソース一式と依存パッケージを使い、プロジェクト直下で実行する。

```powershell
python replay_observations.py "logs/input_events/<セッションファイル>.jsonl"
```

終了行のあるセッションを使う。稼働中・強制終了・破損したセッションを、このコマンドで完全と認定しない。入力blobも必要。ソース内容やPython・pandas・NumPyのバージョンが違う場合は、一致するチェックアウト・環境で検証する。

再生は本体の起動コードをimportせず、対象の既存特徴量・シグナルメソッドだけを取り出して実行する。`.env` の読み込み、DB接続、API接続、実注文、通知を行わない。元の記録ファイルへ書き込まない。

検証範囲：

- 実際の特徴量・スコア・フラグが保存したハッシュと一致すること。
- 保存した確定足と待機状態から同じエントリー方向になること。参照IDがある場合は、その特徴量スナップショットと実際に使った2本の指標値も一致すること。
- 保存した水準・観測価格・時計・利益保護状態から同じ決済理由・次の保護状態になること。

SR候補や約定・口座情報は保存するが、この段階ではSRの生成過程や口座台帳全体を再生しない。決済検証には記録された基本TP/SLを使う。paperのDBルールは未保存のため、paperセッションの特徴量再生を完全と認定しない。未知のイベント種別や再生対象のないセッションも成功扱いにしない。

出力は対象別の検証件数、履歴欠損のあるスナップショット数、検証範囲と未検証範囲を含む。`live_equivalent=false` を維持する。この機能は、変更した戦略の利益や、未記録期間の実約定を証明するものではない。

## 配置

本番反映時には既存のランタイムファイルに加え、`strategy_inputs.py` と `strategy_recording.py` を同時に配置する。オフライン検証側には `replay_observations.py` も必要。今回の記録機能にDB追加変更はないが、このブランチの実約定会計用マイグレーションは引き続き必要。配置後は全コードをそろえてプロセスを再起動する。

このローカル作業では本番接続・配置・再起動は行わない。
