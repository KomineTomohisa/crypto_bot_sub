# 戦略の版管理と発注しない並行比較

`feat/versioned-strategy-shadow` は、2026-11-22の探索結果から選んだ候補を、従来戦略と共通の判定経路で検証するための変更。候補の検証期間には赤字があり、将来の優位性は未確認。本番の初期設定は従来戦略のまま。

## 1. 確定足2本のADX条件

`baseline_v1` は従来の条件。`adx30_no_short_lock_v1` は従来の方向シグナルに加えて、直前の連続した確定15分足2本の **raw `ADX` が両方30以上100以下** の場合だけエントリーする。ADXのスコアではない。欠損・真偽値・非数・無限大は見送る。ロングとショートの両方に適用し、既存のクールダウンと足の時刻検査も残す。

`strategy_decisions.entry_side(..., policy=...)` はliveとバックテストの共通入口。候補のlive発注には、その版・方向・判定足が一致する共通入口の確認情報も必要。

## 2. Short利益保護の切替

従来版は含み益0.75%到達後の0.25%利益保護を維持。候補版は新規の利益保護を起動しない。通常の損切り、利確、逆シグナルによる保護水準の調整、72時間の強制決済は引き続き共通コードで動く。すでに起動済みの利益保護をOFFへ戻すことはしない。

```powershell
python crypto_bot_sub.py backtest --days 30 --strategy-policy adx30_no_short_lock_v1 --backtest-costs configs/backtest_costs_reference.json
```

Pythonからは `bot.backtest(30, policy='adx30_no_short_lock_v1', costs=config)`。終了・例外時に実行前の戦略設定と建玉の設定へ戻す。各取引と集計JSONに設定を記録する。

探索用の `research/replay_engine.py` も、1%で利益保護を起動する比較ケースではその値を明示的な設定として新規仮想建玉へ固定する。従来の探索ケース名だけを残して実際には0.75%を使ってしまうことを防ぐ。既存の探索結果フォルダは上書きしない。

## 3. 建玉ごとの設定

liveの新規注文はPOSTの前に、既存の発注台帳の `context.strategy_policy` へ版・ADX条件・利益保護の有無・起動幅・保護幅を保存する。既存JSON列を使うため、この変更自体にDB移行は不要。

照合時には口座と各建玉IDに紐づくエントリーの設定を取得する。代表IDがなくなる部分決済でも、残ったIDから復元する。新規エントリー用の設定を変えても既存建玉には流用しない。履歴のない旧建玉・外部建玉は従来版として扱う。設定の破損や異なる版の混在では従来の利益保護を優先する。利益保護の起動済み状態と保護価格は既存の `exit_protection` 保存・復元を維持する。

## 4. 仮想資金で並行比較

```powershell
python crypto_bot_sub.py live --shadow-costs configs/backtest_costs_reference.json
```

`--shadow-costs` を指定したliveだけで有効。`--strategy-policy` を指定しなければ、実注文は従来版のまま。候補版を実注文に使う切替は別途 `--strategy-policy adx30_no_short_lock_v1` が必要。この作業では本番起動コマンドを変更しない。

- 別ワーカーで公開APIの営業状態・時刻付き価格・数量ルールを読み取り、SR情報も一度取得して両方の仮想口座へ渡す。仮想口座は秘密鍵・実注文API・発注サービスを持たない。
- 両方とも同額の初期資金・取引予算・同じ費用シナリオから開始。エントリー可否、保有、資金不足、利確・損切り・利益保護、手数料、06時JSTの持越料を独立して計算する。実建玉は引き継がない。
- 本番ループでは最大6行の特徴量のコピーと容量制限付きキューへの投入だけを行う。価格GET、SR読取、ファイル保存はワーカー側。遅延・通信障害・満杯キューを記録し、比較側の例外で実注文の判断や決済監視を停止しない。
- 古い・欠損した特徴量やSR読取失敗では新規仮想エントリーを見送る。仮想建玉は既存の保護水準・通常設定へのフォールバックと、観測できた新しい価格で監視する。価格が取得できない間の仮想約定は作らない。
- 完成足の過去の高安で仮想決済しない。観測した現在価格で判定する。観測の間に起きた価格変動や、再起動中の利確・損切り到達は復元できない。

`shadow/<口座識別子のハッシュ>/state.json` へ両方の資金・建玉・版・保護状態・クールダウン・判定足の重複防止・費用・比較結果を原子的に保存し、再起動時に復元する。同じ比較フォルダにはOSによる排他ロックをかける。保存破損やソース・設定の不一致時に仮想資金を黙ってリセットせず、比較だけを無効化してログへ残す。新しい比較を始める際は、停止中に既存フォルダを退避して履歴を保管する。

`state.json` の `state.report` とログで、従来版・候補版の純損益、含み損益、手数料、持越料、資金・建玉・取引数と評価額の差を確認する。実注文結果は別に記録し、同じシグナルの仮想エントリーと実約定の価格差も出す。実取引との損益差は、開始時の保有や約定・費用が異なるため、戦略の優劣を直接示す値とは扱わない。

`observations/*.jsonl` には初期状態・特徴量・共有価格・SR・数量ルール・実注文の要約・欠測・状態チェックポイントを記録する。対応するソースでネットワーク接続なしに再生できる。

```powershell
python strategy_shadow.py shadow/<口座ハッシュ>/observations/<記録ファイル>.jsonl
```

仮想約定は「観測lastにシナリオのスプレッド・滑りを加算」した推計。実際の板、発注遅延、分割約定、余力、APIの拒否や未確定注文を再現するものではない。建玉の元本全額を仮想資金から拘束する保守的な資金モデルを使う。持越料は06時前に最後に観測した価格を使用し、実費の確定値ではない。

この実装のテストは外部HTTP・メール送信を禁止し、永続化の検証には専用のlocalhost PostgreSQLを使用する。本番DB・実注文は使わない。
