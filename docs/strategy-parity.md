# 本番とバックテストをそろえる基準

目標は「同じ観測データ・設定・口座状態・約定結果を入力すれば、同じ注文意図と次の状態になること」。本番と同じ成績になることや、過去のローソク足から実際の成行約定を復元できることは意味しない。実注文を過去へ追加した場合の板の変化も、足データからは分からない。

## 現在の共通化範囲

| 対象 | 状態 |
|---|---|
| 確定足2本による新規方向・Short優先・クールダウン | 同じ `entry_side` と `next_entry_time` |
| ATR/ADX等による基本TP/SL | 同じ `calculate_dynamic_exit_levels`。ただしSRの取得状態は未統一 |
| 到達判定・決済理由・Short利益保護・72時間決済 | 同じ `_evaluate_exit_event` と純粋判定関数 |
| 日跨ぎの建玉・保護状態 | 維持。検証終了時の状態は実行前へ復元 |
| 全銘柄の資金の時間順序 | 検証は単一のイベント列。同時刻の優先規則はliveも共通 |
| 損益数量 | 調整後数量×約定価格差 |
| 特徴量の入力範囲・初期化位置 | `prepare_strategy_inputs` でJSTの前々日0時から観測時刻までを共通化。時間足は確定足のみ |
| 本番入力と判断の記録・再生 | 圧縮入力と連番付きJSONLを保存。特徴量・エントリー方向・決済判定の一致をオフライン検証 |
| 実約定 | liveは取引所の約定。検証は次足始値・足終了時終値の代理値 |
| 費用・余力・数量ルール | 費用シナリオで手数料・スプレッド・滑り・持越料を時系列反映可能。1倍元本拘束・従来の数量調整を維持し、GMOの当時の明細・数量ルールとは未一致 |

共通の決済関数へ同じ価格・時刻・水準・建玉状態を与え、live/paper/backtestで決済理由・保護状態が一致するテストを実施する。これはデータ取得から発注まで全体の同等性を証明するテストではない。

## 本番との一致を主張する前に必要な作業

1. **入力範囲の共通化を維持する。** EMA等の履歴範囲・初期化・未確定足は共通処理へ移した。記録した入力と計算結果をオフラインで照合する。paperのDB除外ルールとliveのコード内ルールの統一は残る（F15）。
2. **SRを過去時点で復元する。** 各判断時点までに確定した時間足から生成し、同じ30日等の設定・同じスナップショットをエントリーと決済へ渡す。更新済みの現在のSRを過去判定へ使わない（F13）。
3. **記録から執行・口座まで再生する。** botが取得したGMOの時刻付きbid/ask、数量ルール・費用率・余力、注文結果の主要項目の記録を追加した。未確定注文の全状態遷移・分割約定・日次費用明細まで同一入力で再生する経路は残る。手数料・日次費用が不明な取引を純損益確定にしない（F12・F14）。
4. **観測イベントの粒度を合わせる。** 15分OHLCには5分ごとの監視や近接時の100ms観測、TP/SLの到達順、建玉後だけの価格区間がない。録画した価格・判断イベントで再生する経路と、OHLC近似の経路を区別する。通信断や再起動も同じイベントテストへ含める（F17）。

この順で差を閉じ、同一イベント列に対する注文意図・数量・決済理由・保護状態・費用・残高の一致を確認してから、本番と共通の検証と呼ぶ。現状のJSONは `live_equivalent=false` を保存し、利益が出たことだけでこの検証を省略しない。

記録とオフライン検証の実行方法・検証範囲は `docs/input-recording.md` に記載する。

ADX条件・Short利益保護の版管理と、実注文を出さない従来版／候補版の並行比較は `docs/versioned-strategy-shadow.md` に記載する。候補版は明示した場合にだけ使用し、本番の初期設定は従来版を維持する。

## 本番への影響

### 費用込みバックテストの使用方法

`backtest(days, costs=config)`または以下のCLIで明示した費用シナリオを使用する。未指定は従来の費用ゼロ比較を維持し、`costs_included=false`と記録する。ライブ・paperの売買設定には適用しない。

```powershell
python crypto_bot_sub.py backtest --days 30 --backtest-costs configs/backtest_costs_reference.json
```

このCLIは従来のボット起動・データ取得経路を使う。隔離したテストは`python -m pytest tests/test_backtest_costs.py tests/test_backtest_continuity.py -q`で実行する。本番DBやAPIキーをテストに渡さない。

参考JSONは2026-11-22に確認したGMO取引所レバレッジのTaker手数料をLTC/XRP/ETH/BCHは0bp、SOL/DOGE/ADAは片道3bp、持越料を1日4bpとして固定する。全スプレッド2bpと片道滑り1bpは検証用の仮定で、実測値ではない。過去の料金改定を復元していないため、任意の過去期間の実費とは呼ばない。料金出典： https://coin.z.com/jp/corp/guide/fees/ 。設定の`name`・`source`・`notes`・全係数を結果に保存する。

設定は`name`、全対象銘柄の片道`fee_bps`、共通の`spread_bps`（全幅）、`slippage_bps`（片道）、`carry_bps_per_day`を必須とする。単位は1bp=0.01%。未指定銘柄の費用を自動的に0へせず、誤記した設定キー・負数・非有限値・真偽値を拒否する。異なるコスト仮定の比較は設定JSONを複製し、別名・別出力先で行う。

BUYは参照価格へ半スプレッドと滑りを加え、SELLは引く。ロング・ショートの新規と決済で符号を切り替える。数量調整後の約定価格×数量で片道手数料を算出し、新規時に元本と新規手数料の両方を現金から引く。手数料不足時は見送り、決済時は元本と売買損益を戻して決済手数料を引く。約定価格に織り込んだスプレッド・滑りを現金から再度引かない。

持越料は建玉保有中の06:00 JSTを過ぎる際に、その時点より前に観測した最新参照価格×数量×日率で費用を引く。新規時刻と同じ06:00は課金せず、決済時刻・期間末と同じ06:00は課金する。日跨ぎや欠損期間に複数回の締め時刻があれば各回を1度だけ処理する。将来の足終値は使わず、参照価格・その観測時刻・課金時刻を保存する。これはGMOの公式日次精算明細を再現したものではなく、最後の観測価格による近似。記録欠損時も古い参照価格になることをイベント時刻で識別できる。

取引の`profit`・`profit_pct`と勝率・PFへ渡す値は、約定価格ベースの売買損益から新規・決済手数料と持越料を引いた純損益。`gross_profit`は約定価格ベース、`reference_gross_profit`は摩擦適用前の参照価格ベース、差の`execution_cost`は摩擦の影響。JSON明細・Excelの取引ログには費用内訳と`cost_status=scenario_estimate`を保持する。

未決済建玉の新規手数料・持越料も支払時点で現金から引き、`open_costs_paid`へ分離する。完了取引の`realized_profit`へ未決済費用を重ねて入れない。検算式は`現金+拘束元本=開始資金+決済純損益−未決済の支払済費用`、`期末純資産=現金+拘束元本+含み損益`。含み損益には未発生の決済手数料・決済時の摩擦を含めず、結果の`valuation_excludes_future_exit_costs=true`を維持する。

`live_equivalent=false`を維持する。足内の到達順序、過去SR、GMOの当時の数量規則、証拠金・ロスカット・資金調達は引き続き未再現。持越費用等で現金が負になる場合は`negative_cash_observed=true`を保存し、架空の強制決済を追加しない。料金・参照価格・締め境界の近似も結果の制限事項である。費用計算の実装が正しいことと、戦略の将来収益性は別に評価する。

ここまでの共通化は本番のエントリー方向選択、同時刻の監視優先順位、両水準到達時の決済理由にも影響し、本番へ反映済み。2026-11-22には保護状態の永続化と価格検証も配置した。追加の実注文による疎通試験は行わず、模擬取引所でのテストと配置後の稼働確認を行っている。これは上記の未再現項目を解消したという意味ではなく、`live_equivalent=false`を維持する。反映内容は `docs/execution-accounting.md` の累積変更を参照。
