# 本番とバックテストをそろえる基準

目標は「同じ観測データ・設定・口座状態・約定結果を入力すれば、同じ注文意図と次の状態になること」。本番と同じ成績になることや、過去のローソク足から実際の成行約定を復元できることは意味しない。実注文を過去へ追加した場合の板の変化も、足データからは分からない。

## 現在の共通化範囲

| 対象 | 状態 |
|---|---|
| 確定足2本による新規方向・Short優先・クールダウン | 同じ `entry_side` と `next_entry_time` |
| ATR/ADX等による基本TP/SL | 同じ `calculate_dynamic_exit_levels`。ただしSRの取得状態は未統一 |
| 到達判定・決済理由・Short利益保護・72時間決済 | 同じ `_evaluate_exit_event` と純粋判定関数 |
| 日跨ぎの建玉・保護状態 | 維持。検証終了時の状態は実行前へ復元 |
| 全銘柄の資金の時間順序 | 検証は単一のイベント列。同時刻の優先規則はliveも共通 |
| 損益数量 | 調整後数量×約定価格差 |
| 特徴量の入力範囲・初期化位置 | `prepare_strategy_inputs` でJSTの前々日0時から観測時刻までを共通化。時間足は確定足のみ |
| 本番入力と判断の記録・再生 | 圧縮入力と連番付きJSONLを保存。特徴量・エントリー方向・決済判定の一致をオフライン検証 |
| 実約定 | liveは取引所の約定。検証は次足始値・足終了時終値の代理値 |
| 費用・余力・数量ルール | 検証は費用なし・1倍元本拘束・従来の数量調整。GMOの当時の明細・数量ルールとは未一致 |

共通の決済関数へ同じ価格・時刻・水準・建玉状態を与え、live/paper/backtestで決済理由・保護状態が一致するテストを実施する。これはデータ取得から発注まで全体の同等性を証明するテストではない。

## 本番との一致を主張する前に必要な作業

1. **入力範囲の共通化を維持する。** EMA等の履歴範囲・初期化・未確定足は共通処理へ移した。記録した入力と計算結果をオフラインで照合する。paperのDB除外ルールとliveのコード内ルールの統一は残る（F15）。
2. **SRを過去時点で復元する。** 各判断時点までに確定した時間足から生成し、同じ30日等の設定・同じスナップショットをエントリーと決済へ渡す。更新済みの現在のSRを過去判定へ使わない（F13）。
3. **記録から執行・口座まで再生する。** botが取得したGMOの時刻付きbid/ask、数量ルール・費用率・余力、注文結果の主要項目の記録を追加した。未確定注文の全状態遷移・分割約定・日次費用明細まで同一入力で再生する経路は残る。手数料・日次費用が不明な取引を純損益確定にしない（F12・F14）。
4. **観測イベントの粒度を合わせる。** 15分OHLCには5分ごとの監視や近接時の100ms観測、TP/SLの到達順、建玉後だけの価格区間がない。録画した価格・判断イベントで再生する経路と、OHLC近似の経路を区別する。通信断や再起動も同じイベントテストへ含める（F17）。

この順で差を閉じ、同一イベント列に対する注文意図・数量・決済理由・保護状態・費用・残高の一致を確認してから、本番と共通の検証と呼ぶ。現状のJSONは `live_equivalent=false` を保存し、利益が出たことだけでこの検証を省略しない。

記録とオフライン検証の実行方法・検証範囲は `docs/input-recording.md` に記載する。

## 本番への影響

ここまでの共通化は本番のエントリー方向選択、同時刻の監視優先順位、両水準到達時の決済理由にも影響し、本番へ反映済み。2026-11-22には保護状態の永続化と価格検証も配置した。追加の実注文による疎通試験は行わず、模擬取引所でのテストと配置後の稼働確認を行っている。これは上記の未再現項目を解消したという意味ではなく、`live_equivalent=false`を維持する。反映内容は `docs/execution-accounting.md` の累積変更を参照。
