# 売買処理・会計・シグナル計算の修正

対象はレビューのF01〜F10、およびF11・F12の共通判定と時刻順処理。新しい戦略条件の最適化や、本番への配置はこの変更に含めない。本番と検証の残る差は `docs/strategy-parity.md` に記載する。

## 追加修正：決済方向とDI参照（F06・F07）

`buy_signal=Short`、`sell_signal=Long`という既存の売買対応に合わせ、ロング保有時の逆方向をbuy、ショート保有時の逆方向をsellに修正した。損切り調整は確定足4本中3本以上の逆方向シグナルで開始し、同方向が確定足で2本連続したら解除する。判定本数・調整率・解除の優先順位は維持する。

DIは特徴量生成が使う `plus_di14` / `minus_di14` を優先する。旧形式の入力で列が存在しない場合のみ `DI+` / `DI-` を互換用に参照する。両値は同じ直近確定足から読み、欠損を除去して別の足の値に置き換えない。一方が欠損・非有限・負ならDIによる逆行判定を適用せず、ATR/ADXによる保護水準は計算を続ける。

全決済・別の建玉への入れ替わり時に、逆方向SL調整と直前の保護水準キャッシュを初期化する。一部決済で建玉IDの一部が残る場合は状態を維持し、残った建玉の利益保護を解除しない。建玉取得の一時失敗でも初期化しない。paper/backtestでは新規建玉の開始時にも初期化する。

この追加修正にDB変更はない。

## 追加修正：足・ATR欠損時の決済監視

足の取得失敗時は、既存建玉の監視へ空のDataFrameを渡して現在価格による決済判断を継続する。この経路で`ATR`列を直接参照していたため発生した`KeyError: 'ATR'`を修正した。空データ、ATR列欠損、確定足不足、確定足ATRの欠損・非数値・非有限・0以下・真偽値は、例外ではなく代替の保護水準を使う入力状態として扱う。ADX列そのものの欠損も同じ経路とする。

末尾を未確定足とする既存の入力形式に合わせ、ATRは直近確定足（末尾から2行目）から直接読む。欠損行を除去して位置をずらさず、過去の別の足や未確定足のATRを代入しない。全行が正常な入力でのATR/ADX倍率、DI、逆方向シグナル、SRの計算は維持する。確定足ATRが欠損している入力や、1行しかない入力では、従来選ばれ得た別の足の値に代わり、以下の代替処理を使う。

同じ銘柄・方向・建値について最後に正常計算できたTP/SLがあれば、そのコピーを最優先する。設定の再取得やSRの再計算を必要とせず、逆方向SL調整の状態も維持する。正常水準がなければ、既存の基本設定と`fallback_exit`を使う。代替値を正常計算のキャッシュへ上書きしない。現在価格でのTP/SL、Short利益保護、72時間の保有期限は既存の共通決済判定で処理する。足の不足による新規エントリー抑止も維持する。

欠損状態に入った時と理由・代替元が変わった時にWARNINGを出し、同じ状態の連続呼び出しでは繰り返さない。正常計算に戻ったらINFOで復旧を記録する。想定外の計算エラーは引き続きERRORと例外情報を記録する。全決済・建玉入れ替え時には対象銘柄の状態を初期化し、バックテストの正常終了・例外終了でも実行前のログ抑止状態へ戻す。この状態と直前の正常水準はメモリ上にあり、プロセス再起動後は正常水準を再計算できるまで基本設定を使う。

この修正単独で追加のDB移行は不要。新しいブランチの親に含まれる決済予定・通知の変更を一緒に本番へ反映する場合は、後述の002・003とモジュール一式の要件が適用される。

## 追加修正：MACD正規化の未来情報混入（F09）

`signal_scoring.py` にMACD計算を分離した。時点tの基準は `t-50..t-1` の50本から計算した20%・80%分位点で、当該足tと後続足を含めない。15分足では過去12.5時間分に相当する。ヒストグラム70%・MACDとシグナルの差30%という配合は維持する。

最初の50本、欠損・非有限の入力、基準の分位点が同値の場合はスコアをNaN、`macd_score_ready=False` とし、両方向の新規シグナルを抑止する。過去50本内に欠損があれば、その欠損が窓から外れるまで再開しない。既存建玉の決済監視は継続する。重み付き合計内だけで使う中立値0.5は、未確定のMACDをエントリー可能にするものではない。

同時に、特徴量初期化時の出来高平均・ATR補完を、その時点までのデータで計算する形へ変更した。合計スコア正規化の後方補完（bfill）も取り除き、後続のデータから過去値を補わない。

計算方式ID `macd_prior50_q20_q80_v1` と窓・分位点・未確定時の動作を、シグナルrawとバックテストJSONの `scoring.macd` に保存する。方式IDはstrategy versionのハッシュにも含める。コード全体の版同定（F14）は別の修正対象。

この変更でスコアの意味とエントリーの採否・件数は変わり得る。「0.5以上0.8未満」の除外条件の数値は維持するが、旧スコアでの履歴除外結果を新方式の利益改善とみなさない。新方式でコストを含む再検証が必要。この段階では収益性のバックテストは実施していない。

本番との約定再現、過去時点のSR、取得データの欠損品質などは引き続き別の修正対象。

## 追加修正：バックテストの連続処理と期間末評価（F10）

実行開始時に検証期間をJSTで固定し、`開始日00:00 <= 足の開始時刻 < 実行日00:00` の足を再生する。日別ファイルを時刻順に結合し、特徴量は各観測時点でliveと同じ履歴範囲（JSTの前々日0時以降）から計算する。期間前の履歴は約定・シグナル出力の件数に含めないが、開始時の直近確定足として参照できる。指標の初期化位置は共通の履歴方針に従い、建玉と保護状態は日付にかかわらず継続する。

建玉方向・建値・数量・エントリー時刻と指標・拘束元本・保護状態・再エントリー待ちは日付が変わっても保持する。従来の「末尾96本」をやめ、欠損日の前日フォールバックも無効にした。同じ足の重複取得は1回にまとめ、同時刻の足に矛盾があれば明示的に中断する。欠損区間を挟む足を連続2本の新規シグナルとして扱わない。既存建玉は欠損日も保持し、次に観測できた足から監視を再開する。

最終足では強制決済しない。未決済の方向・建値・数量・開始時刻、最終観測終値と評価時刻（その足の終了時刻）、`数量 × 方向付き価格差` の含み損益を `results.<symbol>.open_position` に保存する。`symbol_profit` と `total_profit` は決済済みの損益だけを表し、含み損益を実現益や勝敗件数へ加算しない。JSONの `period` に正確な期間、`valuation` に評価方式・実現損益・含み損益・拘束元本・費用未控除を記録する。欠損があれば評価時刻は期間末より古くなり得る。拘束元本は従来の検証上の資金拘束額であり、本番の証拠金実額ではない。

バックテスト専用の建玉数量・保護状態・利益集計を使用し、正常終了・例外のどちらでも実行前のオブジェクト状態へ戻す。戻り値とJSONを検証結果として使用する。再生中のエラーや必要データの全欠損を黙って飛ばして合格結果を保存しない。起動済みの売買ループと同じbotインスタンスでの同時実行は想定しない。

内部の足時刻・JSONはJSTのタイムゾーンを保持する。既存のExcel出力2経路へはコピーを渡し、そのコピーの日時とシグナル履歴のインデックスだけをJSTのタイムゾーンなし日時に変換する。Excelの日時制限を回避し、内部記録の時刻を変更しない。

F10の検証は日別/一括データの一致、日跨ぎの両方向決済・保護状態・再エントリー、期間末の未決済評価、欠損日・期間境界・状態復元を対象とする。続く共通判定・時刻順処理の仕様は下記に記載する。DB追加変更は不要。

## 追加修正：共通の売買判断と全銘柄の時刻順処理（F11・F12の一部）

`strategy_decisions.py` に、確定足2本のエントリー方向、Short利益保護、TP/SL到達・72時間決済、次の15分境界までの待ち時間を分離した。liveとbacktestが同じ関数を呼ぶ。Shortの優先順位はliveに合わせ、両方向のシグナルが同時に立つ場合もShortを優先する。未確定・古い・非連続の足から新規エントリーしない。最終決済意図は `_evaluate_exit_event` を共通で使用する。時刻は引数として与え、過去検証で現在のPC時刻を使わない。

Shortは観測価格で含み益0.75%以上に到達した後、最低0.25%の利益保護SLを維持する。保護開始前の同じ足の高値だけで新しい保護SLへの到達としない。建玉開始前の同一足高安も、その建玉の到達価格としては使用しない。TP/SL両方に触れた足は到達順序が分からないため、決済理由はSL側を優先する。理由が「利益確定」でも成行の実損益が利益になる保証はなく、勝敗は約定損益で集計する。

バックテストでは足の高安・終値をその足の終了時刻で観測し、決済価格は終値を成行価格の代理値に使う。閾値への架空の有利な約定をやめたが、bitbank終値はGMOの実約定価格ではない。エントリーは引き続き次足始値の代理価格であり、同じ足でのエントリー直後の追加監視や本番の5分・100ms観測系列は再現しない。

銘柄ごとの並列再生を廃止し、全銘柄のイベントを観測時刻順に処理する。同時刻は既存建玉の監視・決済を先に、新規エントリーを後にし、同種イベントは銘柄名順とする。liveの各周回も同じ優先関数を使う。将来の決済代金を過去の新規注文に使わず、検証の使用可能現金が元本を下回れば見送る。実現損益は固定TRADE_SIZEではなく、数量調整後の実数量×価格差で計算する。検証口座は費用なし・元本1倍拘束の近似モデルであり、本番の取引余力・証拠金計算と同一ではない。

JSONに判断方式ID `shared_entry_exit_v1`、`execution_model`、`account_model`、使用可能現金、共通の特徴量履歴方式、未再現項目を記録する。現状は `live_equivalent=false` とする。過去SR、当時の数量・手数料ルール、GMO価格系列などの差が残るため、本番同等や費用控除後の収益性の証明として扱わない。

## 変更する動作

- LIVE注文は `LiveExecutionMixin` → `ExecutionService` を通す。従来のLIVE `place_order` 経路は拒否する。
- DBへ注文意図を保存し、送信の所有権を取得してからPOSTを1回送る。POSTのHTTPリトライ・リダイレクト・外側の再送を無効化した。
- `clientOrderId` はハイフンなしUUID。送信後に応答やDB接続を失っても、同じIDで注文と約定を照合する。次の判定足や再起動で別注文として再送しない。
- 注文意図は口座単位で1件ずつ処理する。未確定の注文が残る間は、新たな注文意図を送信しない。アプリのメモリ上のロックだけでなく、DBの排他制約と送信前の状態更新で制御する。
- 同じ銘柄・方向・判定足での新規注文は重複させない。過去の成功結果を再生して、決済済み建玉をメモリに復活させない。
- 建玉の残量から注文の約定量を推定しない。注文ID・約定ID・建玉ID・方向・OPEN/CLOSE・数量が一致するものだけ記録する。
- `EXECUTED` 等の注文状態だけで成功にせず、実約定の合計数量との一致を確認する。約定APIの反映待ちでは未確定状態を保つ。
- 分割約定は数量加重平均。部分決済は実際に閉じた数量だけ会計へ反映し、残量と利益保護状態を維持する。
- 建玉の同期には数量加重平均と取引所の時刻を使う。取得失敗を「建玉なし」としてクリアしない。記録した建玉が決済約定なしで消えた場合は新規注文を抑止する。
- EMA乖離の判定をIndexに依存しない真偽条件に修正。無効なEMAではエントリーを抑止する。
- TP/SL計算の異常時は、同じ建玉で直前に計算できた値、なければ正常系と同じ方向・距離の基本値を使う。正常時の戦略上の距離設定は維持する。

### 分割決済と照会の反映待ち

注文・約定の照会で一時的な反映差がある場合、GETの照合だけを最大3回実行する。待機は0.2秒、0.5秒で、処理開始から2秒以上経過した場合は追加試行を開始しない。この2秒はHTTP通信全体の締切ではなく、各リクエストのタイムアウトは従来どおり。ID・方向・数量上限等の不整合は検証を維持し、注文POSTは再送しない。`EXECUTED`で数量が未反映の場合も未確定として扱う。照会項目の定義は[GMO公式の注文情報取得](https://api.coin.z.com/docs/#orders)を参照。

決済条件が成立したら、追加の建玉照会や注文の送信可否を調べる前に`bot_close_batches`へ要求を保存する。最後に正常確認した建玉スナップショットから対象IDと数量、決済理由を固定し、新しい照会の確認前は`payload.positions=null`とする。建玉照会が失敗した場合や別注文の照合待ち中にも、要求は注文台帳と独立して残る。

照会が回復したら、固定した対象IDと数量が一致するスナップショットを一度だけ確定・保存してから決済注文を送る。待機中に追加された対象外の建玉は含めない。反映待ち、部分キャンセル、プロセス再起動の後も、保存済みの対象IDと記録済み決済数量から残りを復元する。次のサイクルで価格が変わっても、新たな決済シグナルを待たず継続する。

未完了の対象がある間は新規エントリーを抑止する。予定の保存と注文準備は同じ口座のDBロックで直列化し、同一銘柄での重複した予定や保存後の対象の差し替えを防ぐ。注文台帳の未確定1件制限は維持する。DBロック内でも残量を再検証し、古いスナップショットで決済を重ねない。全対象の数量が記録済み約定で閉じた後に予定を完了し、互換用の`context.close_batch_done`も同じトランザクションで付ける。

この変更には`migrations/002_durable_close_batches.sql`が必要。新しいテーブル1件と索引を追加し、前回版が`context.close_batch`に保存した未完了予定を引き継ぐ。既存の注文・約定・損益は書き換えない。移行後も旧プロセスが未完了予定を書き込む可能性に備え、実行時にも未登録の旧形式を読み取り、再開前に新テーブルへ保存する。

最後に確認できたIDや数量自体が不足している場合も要求は保存するが、後から現れた建玉を推測で紐付けて発注しない。対象の消失・方向変更・数量変化も未解決として残し、取引所明細と台帳の照合を必要とする。DBへ要求を保存できない場合は、追加の建玉照会と発注へ進まない。

この要求・確定の2段階は既存の002のJSON列で扱い、追加のDDLは不要。前回版が保存した`positions`配列のある決済予定も継続できる。未確定要求を残して以前のコードへ戻すと、その形式を扱えないため自動継続を前提としない。

### 決済が滞った場合の通知

保存した決済要求が未完了のまま2分経過したら、既存のメール・LINE通知経路へ警告する。その後も未完了なら、最後に送信できた警告から30分ごとに再通知する。全対象の数量が記録済み約定によって決済済みになったら、警告の送信に成功した要求について復旧通知を送る。建玉照会が回復しただけでは復旧扱いにしない。警告を送る前に完了した要求は通知しない。

`notification_settings.enabled`と`send_on_error`が両方有効な場合に監視する。既存の通知先・認証設定を使用し、新しい宛先は追加しない。通知本文には銘柄、短縮した要求ID、要求日時、経過時間と確認状況を記載し、価格・数量・API応答・認証情報は含めない。

| 環境変数 | 初期値 | 意味 |
|---|---:|---|
| CLOSE_STALL_ALERT_SECONDS | 120 | 要求の保存から初回警告までの秒数 |
| CLOSE_STALL_REMINDER_SECONDS | 1800 | 最後に警告を送信できてから再通知までの秒数 |
| CLOSE_STALL_RETRY_SECONDS | 300 | 通知送信失敗後の再試行間隔（秒） |

設定値は1〜604800の整数とし、無効値は初期値へ戻す。実際の検出時刻は売買ループの次回照合時点となる。通知送信は最大8件の待機キューと専用のdaemonスレッドで処理し、SMTPやLINEの遅延によって売買ループを待たせない。キュー満杯・通知処理失敗でも決済処理を継続する。既存の他用途の通知の同期処理は維持する。

送信履歴と600秒の送信権の期限をDBに保存し、再起動や並行プロセスによる通常の重複通知を抑止する。送信中のプロセスが終了した場合は期限後に再試行する。メールまたはLINEの少なくとも一方が送信成功を返した場合に履歴を更新する。これは配信サービスによる受付の確認であり、利用者の閲覧確認ではない。サービス受付後・DBへの成功記録前にプロセスが停止した場合などは重複する可能性がある。

この通知機能には、002の後に`migrations/003_close_stall_notifications.sql`を適用する。`bot_close_batches`に通知専用の6列を追加し、決済対象のJSON、注文、約定、損益は変更しない。003は同テーブルの所有者権限で実行し、既存所有者は変更しない。実行時の自動DDLは行わず、起動時に必要な列を確認する。直前版へ戻しても追加列は残せるが、未完了要求を扱える版を選ぶ必要がある。

### エントリー・決済の約定通知

LIVEの通常約定と応答待ち後の照合結果は、`trade_notifications.py`で同じ形式の通知を作る。件名には銘柄、建玉のロング／ショート、新規／決済、全数量約定・一部約定・約定なしを表示する。決済の件名と本文冒頭には、今回の注文で記録された売買損益を手数料控除前として表示する。SELLの決済はロングの手仕舞い、BUYの決済はショートの手仕舞いとして表示し、注文の売買方向と建玉方向を混同しない。

価格・数量・日時・損益は`ExecutionStore.result`と記録済みのtradesを使い、通知時点の現在価格や、既に初期化されたメモリ上の建玉から推定しない。注文数量と実約定数量を分け、一部約定後のキャンセルを全数量約定と表示しない。未確定注文は約定確定メールへ変換しない。日時はJST、価格と数量は小数点以下も表示する。約定代金は価格×数量の金額であり、証拠金額を推定するものではない。

新規注文では、判断足とその終値、採用方向の総合スコア（Longはsell系、Shortはbuy系）、MACDスコア、保存したRSI・ADX・ATR・DI・EMAを表示する。共通判定で確認できた同方向の確定足2本と注文の判断足・方向が一致するときだけ、2本連続の根拠を保存・表示する。旧形式の注文や記録不足では理由を推測で補わず「記録なし」「未取得」とする。保存する指標・通知に載せる項目は限定し、API応答、環境設定、認証情報やDataFrame全体は取り込まない。本文のために新しい市場データやSRを取得しない。

決済では理由、決済分の平均建値、実約定の売買損益、その建値×数量を分母にした損益率、配賦済み新規手数料、決済手数料、手数料控除後損益、保有時間、完了日時、元の決済対象の残数量を表示する。不明な費用は0円にせず未確定とし、日次費用を取引別に配賦していないことも示す。複数建玉の決済は注文ごとの通知であることを明記し、一つの通知を建玉全体の決済完了と扱わない。

既存の`enabled`、`send_on_entry`、`send_on_exit`と配送経路を使う。LIVEの旧エントリー本文との二重送信を避け、同じプロセス内で送信成功を確認した同一約定結果は繰り返さない。過去の確定済み注文を起動時に一括メール送信しない。通知作成・配送の失敗は約定台帳や決済の継続を変更せず、通知用の追加列・DDLは不要。既存通知と同様に配送は同期処理であり、メールの確実な再配送を保証する永続outboxはこの変更では追加しない。

## DBと損益の意味

追加SQL: `migrations/001_execution_accounting.sql`、`migrations/002_durable_close_batches.sql`、`migrations/003_close_stall_notifications.sql`の順に適用する。既存履歴のpnlを再計算したり、近似値を実約定値に見せかけて書き換えたりしない。DDLは起動時に自動実行しない。起動時のスキーマ確認には新しい決済予定テーブルと通知用の列も含む。

| 保存先 | 内容 |
|---|---|
| bot_order_intents | 送信前の注文内容、判定足、状態、clientOrderId、取引所注文ID |
| bot_close_batches | 別注文の照合待ち中でも保存する決済予定。元の対象・数量・理由と完了状態 |
| bot_execution_fills | 約定IDを主キーにした実価格・実数量・実時刻・手数料・決済損益 |
| bot_position_baselines | 変更前から保有する建玉の取引所スナップショット |
| bot_account_fees | 営業日×銘柄×費用種別の徴収・返金実額 |
| bot_fee_sync | 明細が確定済みの営業日までの取得位置 |
| 既存orders/fills/positions/trades | 上記に基づく互換用の記録。約定・建玉・決済を同一DBトランザクションで更新 |

`trades.pnl` は互換性のため売買損益（gross）のまま。新しい記録は `accounting_version='execution_v2'`、古い記録は `legacy_estimate` として区別する。

追加列 `entry_fee`、`exit_fee`、`net_pnl_before_carry` に、取引手数料と控除後損益を保存する。Maker手数料が負なら還元として扱う。変更前からの建玉は新規手数料が不明なので、推測で0円にせずNULLを残す。`cost_status` で未確定を識別する。

決済行は「決済注文意図×建玉ID」の単位。同一注文で約定が後から増えた場合は同じ決済行を更新する。別の注文で残量を決済した場合は別行となる。トレード数を比較するときは、この定義差に注意する。

持ち越し料APIは建玉別の明細を返さないため、取引別への厳密な配賦は行わない。口座・銘柄・営業日単位の実費として保存する。`lastFinalizedDate` を確認し、明細がまだ出ていない日を0円確定としない。初回は直近7日前から取得し、以後は取得済み営業日から追跡する。初回より前の費用の取得は別の履歴補完が必要。

既存の画面・日次統計のpnl表示はgrossの集計を維持する。`ExecutionStore.pnl_summary` は記録済み台帳の構成額であり、入出金・台帳開始前の損益・外部手動取引まで含めた口座の総損益や運用利回りではない。純損益を分析するときは対象営業日と収集範囲をそろえ、費用の確定状況を確認する。

## 資金確認

時価評価総額=`actualProfitLoss`、取引余力=`availableAmount`、拘束証拠金=`margin` として区別する。

注文単位・最小/最大数量・Taker手数料はPublic symbols APIから取得する。数量は切り下げて注文単位に合わせ、最小数量未満は見送る。BUYはask、SELLはbidを使用し、90秒超の古い価格や不正な数値を拒否する。

必要額は `元本 / 適用レバレッジ + 往復取引手数料 + 元本の0.5%の余裕額`。取引余力と円単位で比較する。`GMO_MARGIN_LEVERAGE` は1〜2の範囲で設定する。未指定は保守的に1倍として確認するため、実際のレバレッジが2倍でも余力不足として見送る場合がある。この設定は取引所のレバレッジを変更するものではない。

## 障害時の扱い

- 新しいコードを起動する前に002・003を適用する。既に001が適用済みなら001を再実行する必要はない。002はアプリのDBロールが新しいテーブルを読み書きできる所有者・権限で実行する。003はその決済予定テーブルの所有者権限で実行する。既存の注文・約定テーブルの所有者は変更しない。
- 旧コードへ戻す際は、未確定注文に加え`bot_close_batches`の未完了予定を照合する。最初の注文をまだ作っていない予定は旧コードから見えないため、未完了予定を残したまま旧版へ戻して自動継続されると扱わない。
- 送信前のDB保存・排他取得に失敗した場合は注文しない。
- DBに `SUBMITTING` を保存した後は、送信された可能性があるため読み取り照合を続ける。未確認のまま状態を消したり、新しいIDで再発注したりしない。
- 明確なパラメータ不正・取引規制等の既知エラーだけを拒否確定とする。通信障害、システムエラー、未知の応答は結果不明扱い。
- 約定後に会計更新が失敗した場合はトランザクションを戻す。注文意図は残り、復旧後に実約定から再処理する。
- DB障害時も既存建玉の読み取り監視を継続する。ただし注文意図を永続化できない場合は自動決済も送信できない。決済が必要なときは未確認通知を出す。これは取引所常駐の逆指値を新設する変更ではない。
- 取引所の照会対象期間を過ぎた注文や、手動決済等で記録外の建玉変化があった場合は、取引所明細との個別照合が必要。未確認状態を解除するためだけに注文意図を削除しない。

python -m pip install -r tests/requirements.txt

## 本番反映時の要件

### ローソク足取得のUTC日付と鮮度

APIの日付はUTCで作り、戦略に渡す履歴は従来どおりJSTの前々日0時から確保する。UTCでまだ始まっていない日を要求せず、明示したAPI日付の取得に失敗しても別日をその日として返さない。

更新中の15分足・1時間足等のファイルは30秒で更新する。足の確定境界をまたいだときは30秒未満でも再取得する。過去日はUTC日終了の1分後以降に保存され、期待する全timestampを含む場合に限り長期キャッシュを使う。日付変更前に保存した未完成ファイルは再取得する。無効なOHLCVを後方補完や平均値で作り直さない。

新規注文前には、共通履歴の確定15分足・1時間足の欠損、最新の15分足の存在、OHLCVの整合性を確認する。取得失敗・欠損・古い入力・特徴量生成エラーでは新規エントリーを行わない。既存建玉は古い足の高安を使わず、空の足入力と現在価格で既存の決済経路を続ける。TP/SLはその建玉の直前の有効値、なければ既存の基本値へフォールバックする。取引所への注文意図保存等の既存の制約は維持する。

この変更の本番反映はまだ行っていない。既存の未反映変更を含むため、以下のDB移行・モジュール一式の手順が必要。

このブランチの作成・テストでは本番を変更していない。

DB移行前には、接続ロールのCREATE権限だけでなく、既存のtradesをALTERできる所有者権限も確認する。本番で既存テーブルがpostgres所有、アプリがcryptobotの場合、所有者権限で移行を実行する必要がある。承認された所有者セッションで、新テーブル作成部分だけをSET LOCAL ROLE cryptobotで実行し、既存tradesのALTER前にRESET ROLEすることで、既存の所有者を変えずに追加できる。停止前に移行を検証し、権限不足で停止時間が延びないようにする。

本番へ反映する際は、既存DBをバックアップしてSQLを先に適用し、同じリリースとして以下を配置する。本体1ファイルだけの差し替えでは動かない。

- `execution_store.py`
- `signal_scoring.py`
- `backtest_data.py`

本番入力の記録・オフライン再生については `docs/input-recording.md` を参照。検証用CLIは `replay_observations.py`。起動後に自動で記録するが、このローカル作業では本番への反映は行わない。

`db.py` 全体の上書きは不要。既存のDBエンジンを利用する。起動前に新テーブルとtrades追加列、APIのPublic symbols・ticker/Private orders・executions・openPositions・margin・exchangeFee/historyの参照権限を確認する。注文の疎通確認として実注文を発行しない。
